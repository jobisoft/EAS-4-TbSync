How things work

How EAS-4-TbSync behaves, and why. The host's own mechanisms — the provider handshake, the E:AUTH rule, CANCEL_SYNC — are in the TbSync notes.

EAS calendars are a provider calendar type

Repo: EAS-4-TbSync, with host support in TbSync.

A plain storage calendar cannot tell one kind of write from another: the user editing an event and the sync writing down what the server sent look identical. TbSync used to compensate by pre-tagging each of its own writes so the observer would ignore them, and even then the record it kept was item-level, so a series with one moved occurrence was re-sent whole.

EAS registers its own calendar type, ext-eas4tbsync@jobisoft.de. The two directions become different objects:

directionroutefires provider hooks?
user edits calendar.provider.onItem{Created,Updated,Removed} yes, with the previous item attached
our own sync writes<id>#cacheno

<id>#cache is the storage calendar behind the cached one, reachable via calendars.get(id + "#cache"). Both share an id, so a write there shows up on a normal read immediately.

The hooks do not push. They fire while the platform holds the user's save, so a network round trip there would fail the edit outright when the connection is down. They record; the scheduled sync pushes.

Nor do they hold the record. The provider owns no persistent storage — the host owns accounts, folders and the changelog — so a queue in the provider would be lost on every reload. The hooks report through changelogRecordUserEdit into the same folder.changelog the push already reads. Only the author of the entry changed, which is what lets it carry an exception fingerprint as detail.

  • Only calendars moved. Address books have no provider API, so they are still observed and still use pre-tagging. Both *_by_user and *_by_server remain in use there.
  • *_by_server no longer appears for calendars. The runner still calls changelogMarkServerWrite — it is shared with contacts — but the host drops the call for provider-owned targets. Without that the tags accumulate, one per synced item, because the observer that consumed them has stepped back.
  • The target's lifecycle is ours too. The host has no calendar API at all now, so a rename reaching the folder row and a deletion clearing the binding are both this provider's work. See below.
  • Disabling EAS force-disables its calendars. They become dummy entries until it is enabled again; the data survives.
  • No migration path. Deselect and reselect a folder to rebind it.

Watching our own targets

calendars.onUpdated mirrors a rename into folder.targetName, which is what the manager displays.

calendars.onRemoved is the interesting one, because it fires for two different things: a calendar the user deleted, and every one of ours when our own calendar type unregisters — which happens on each reload, update and disable. Nothing in the event distinguishes them, so the handler asks afterwards instead of trusting it:

  • the calendar is gone → a real deletion → report it
  • it is still there but force-disabled → our type is unregistering → ignore
  • the question cannot be answered at all → we are being torn down → ignore

A verified deletion is reported with FOLDER_TARGET_REMOVED, and the sync key and index are reset first. They described a calendar that no longer exists, and leaving them would bind a fresh empty calendar to a key the server answers with "nothing has changed" — the user would get a calendar that stays empty. Those are the provider's state, so the provider clears them.

This is also why the listener belongs here rather than in the host. The event fires as the provider goes away; a listener inside the provider is being torn down at that moment, while a separate extension that stays alive would see it and act. Which is exactly what used to deselect a folder on every update.

Folders the server drops are the third way a folder stops being synced, after onFolderDisabled and onAccountDeleted. pushFolderList hands back the targets that fell out of the folder table, and this provider deletes them.

Item identity, and why the blob stamp is the authority

Repo: EAS-4-TbSync. Identity lives in the provider; the host only stores the blob it is handed.

The server-id stamped inside each stored blob is the authority for which local item a server item is. custom.indexMap is a cache in front of it.

findExistingByServerId reads the indexMap first and, on a miss, falls back to a lazily-built serverId → itemId map read from the blob stamps, repopulating the indexMap on a hit. The map is built at most once per pass and only when something misses, so a healthy incremental sync never reads the store in bulk.

Both halves matter. The indexMap alone is not enough: a server-initiated resync (Sync Status 3) resets it to [] along with synckey: "0", so every item arrives as an <Add> with nothing to match against. The blob stamps alone are not enough either: a locally-deleted item leaves no blob to read, so the indexMap is the only remaining record of that item's server id.

Recurrence exceptions on EAS 16.x

Repo: EAS-4-TbSync, all in src/modules/eas/calendar-codec.mjs.

Inbound exceptions arrive in two shapes, both gated on the account's syncRecurrence option (off by default): embedded, an <Exceptions> block on the master; and per-instance, one <Change> or <Delete> per occurrence carrying airsyncbase:InstanceId.

Outbound on 16.1 it is per-instance only. The embedded block is not accepted in a Sync request — tested against Exchange, which answers Status 6 for the wrapper itself, whether the exception is keyed by InstanceId or ExceptionStartTime, and whether or not it carries <Deleted>. A control run with the block suppressed and nothing else changed was accepted. [MS-ASCAL] 2.2.2.21 lists Exception as supported on 16.0/16.1 and [MS-ASAIRS] puts InstanceId under calendar:Exception "in a Sync command request and response", so the server disagrees with both.

Two further rules the wire forced:

  • A cancelled occurrence is a <Delete>, not a <Change> carrying <Deleted>. Deleted is only legal inside the embedded block, which 16.x replaced. The 16.x form is ServerId plus airsyncbase:InstanceId, no ApplicationData at all.
  • One instance command per request. Exchange will not take two commands against the same ServerId in one <Commands> block: it applies the first, faults on the second, and answers a global Status 16 that discards the response while keeping what the first did. Every exception of a master shares that master's ServerId — which is also why a modified master sends its exceptions in a separate pass.

Only changed exceptions are sent. The changelog entry carries a fingerprint of the exception set from before the edit — the cancelled instances plus each override keyed by RECURRENCE-ID with a digest of its content — so listInstanceCommands skips a cancellation the server already has and an override whose digest has not moved. An added item has no baseline and sends everything: the server has only just met it. An override is pushed whole, so knowing that one changed is enough.

Already-synced items need a one-time calendar re-download (deselect → sync → reselect → sync) before a codec change affects them, so a fix can look inert on existing data.

The server's UID is discarded on 16.x

Repo: EAS-4-TbSync. Harmless today; MeetingResponse will care.

On 16.0/16.1 the client MUST NOT send <UID> ([MS-ASCAL] §2.2.2.46), so the server mints its own and returns it. We never keep it. Uploading, applyResponses reads ClientId, ServerId and Status from the acknowledgement and drops the rest. Downloading, applyAdd generates crypto.randomUUID() and the server's <UID> is never read.

So on 16.x the iCal UID and the server's UID differ in both directions, invisibly, because nothing consults either. Verified against a live Exchange Online mailbox: five events uploaded with zero <UID> elements came back after a clean resync carrying server-minted IDs of the form 040000008200E00074C5B7101A82E008…. On ≤14.x none of this applies — the UID is client-generated and we send it.

It does not matter today because identity uses the EAS ServerId. It may matter for iTIP traffic, where the UID correlates an invitation with its reply — see Todos.

The sync sequence

Repo: TbSync, with the folder-level half in EAS-4-TbSync's sync-runner.mjs. What actually goes over the wire during one sync, in order, and where the 16.1 recurrence work sits inside it.

One account sync, start to finish

The phases

The account level lives in TbSync's sync-coordinator.mjs: it asks the provider to sync the account, gets a sorted folder list back, and then drives one SYNC_FOLDER per selected folder. Everything below happens inside one of those, in EAS's runOneSync.

Bootstrap
Only when the folder has no SyncKey - a new folder, or one whose key the server rejected. A Sync with SyncKey=0 returns a usable key and no items. This is also what a clean resync is: deselecting a folder throws the key away (and deletes the local calendar), so reselecting starts here and pulls everything down again.
Pull
GetItemEstimate first, purely so the progress bar means something. Then Sync with GetChanges, repeated while the server sets MoreAvailable. Each response carries server-side Add / Change / Delete commands, which are applied locally.
Push
Skipped entirely for a read-only or download-only folder. Otherwise the changelog's *_by_user entries become one or more Sync requests carrying Commands, batched up to the account's item limit. The reply is sparse by design: the server answers only failures, plus the ServerId for each accepted Add. Silence means success.
Instances 16.1
A recurrence exception is not part of its master's payload on 16.1. It is a sibling command carrying the master's ServerId and an InstanceId naming the occurrence - Change for a moved one, Delete for a cancelled one. It therefore cannot be sent until the server has assigned that ServerId, which is why this is its own pass after the push rather than part of it.
Settle
An optional second pull, off by default. Exchange enriches an item after accepting it - UID, DtStamp, organizer - and echoes the result back as a change. Without the wait, that echo is simply picked up by the next sync.

Why the instance pass sends one command at a time

Every exception of a series carries the same ServerId - its master's. Exchange will not take two such commands in one Commands block: it applies the first, faults on the second, and answers a global Status 16 that discards the response while keeping what the first command already did. So each exception travels in its own request.

One command per request is still not enough to avoid Status 16 entirely: the Change above followed a Delete against the same master and faulted anyway, in a request that carried nothing else. The resend worked, so the condition is transient - Exchange settling the master between commands - and [MS-ASCMD] gives exactly that resolution for Status 16: resend the request.

The retry then met Status 7, which is a different thing: the server's copy of the master had genuinely moved on, because the Delete and Exchange's own enrichment had both landed since. The reply carries those changes, so applying them and re-sending resolves it.

Two independent conditions, arriving in sequence. Each needs its own retry allowance - a single shared one is spent by the first, and the second is then reported as a failure for something that would have succeeded.

Reading a sync log

At debug level every request and response is written to the event log as [eas:net] send Sync / receive Sync, with the XML in the entry's details. Useful shapes to look for:

  • <Add><ClientId> - a local item going up for the first time; the reply's ServerId is its identity from then on.
  • <InstanceId> as a sibling of <ServerId> - a 16.1 exception. Inside <ApplicationData> it would be wrong, and Exchange answers Status 6.
  • A bare <Sync><Status>N</Status></Sync> with no Collection - a global status. The whole request was discarded, though side effects of commands it already processed survive.
  • A Collection with Status 1 and no <Responses> - everything was accepted. The server reports only failures.
