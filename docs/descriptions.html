How things work

The mechanisms worth understanding before changing the sync engine or the codecs. The host's own — the handshake, sessions, the E:AUTH rule — are in the TbSync notes.

Our own calendar type

EAS registers the calendar type ext-eas4tbsync@jobisoft.de, so the two directions of a sync are different objects:

directionroutefires provider hooks?
user editscalendar.provider.onItem{Created,Updated,Removed}yes, with the previous item attached
our sync writes<id>#cacheno

<id>#cache is the storage calendar behind the cached one, reachable via calendars.get(id + "#cache"). Both share an id, so a write there shows up on a normal read immediately.

The hooks do not push. They fire while Thunderbird holds the user's save, so a network round trip there would fail the edit outright when the connection is down. They queue; the scheduled sync pushes.

The queue is ours. It lives in this add-on's storage (eas/change-queue.mjs), keyed by the binding the host names in folder.sessionId. The record has to be durable before the hook answers and must not depend on the host being alive — our calendars keep working when it is not. Address books are the other way round: Thunderbird offers no provider API for them, so the host observes those and owns their entries in folder.changelog.

  • *_by_server pre-tags are meaningless for our calendars — nothing observes them — so the runner's mark-server-write call is a local no-op.
  • Disabling the add-on force-disables its calendars. They become dummy entries until it is enabled again; the data survives.
  • There is no migration path from a plain storage calendar. Deselect and reselect a folder to rebind it.

Watching our own targets

calendars.onUpdated mirrors a rename or recolour into the folder row, which is what the manager displays.

calendars.onRemoved is the interesting one: it fires both for a calendar the user deleted and for every one of ours when our calendar type unregisters — which happens on each reload, update and disable. Nothing in the event distinguishes them, so the handler asks afterwards:

  • the calendar is gone → a real deletion → report it;
  • it is still there but force-disabled → our type is unregistering → ignore;
  • the question cannot be answered → we are being torn down → ignore.

A verified deletion is reported with FOLDER_TARGET_REMOVED, and the sync key and index map are reset first: they describe a calendar that no longer exists, and leaving them would bind a fresh empty calendar to a key the server answers with "nothing has changed". Those are our state, so we clear them.

This is also why the listener belongs here and not in the host: the event fires as the provider goes away, so a listener inside it is being torn down at that moment, while a separate extension would see it and act — which is what would deselect a folder on every update.

Item identity

The server-id stamped inside each stored blob is the authority for which local item a server item is. custom.indexMap is a cache in front of it. findExistingByServerId reads the index first and, on a miss, falls back to a lazily-built serverId → itemId map read from the blob stamps, repopulating the index on a hit. The map is built at most once per pass and only when something misses, so a healthy incremental sync never reads the store in bulk.

Both halves are needed. The index alone is not enough: a server-initiated resync (Sync Status 3) resets it to [] along with synckey: "0", so every item arrives as an <Add> with nothing to match against. The blob stamps alone are not enough either: a locally-deleted item leaves no blob to read, so the index is the only remaining record of that item's server id.

The sync sequence

The account level lives in TbSync's sync-coordinator.mjs: it asks the provider to sync the account, gets a sorted folder list back, and drives one SYNC_FOLDER per selected folder. Everything below happens inside one of those, in runOneSync.

Bootstrap
Only when the folder has no SyncKey — a new folder, or one whose key the server rejected. A Sync with SyncKey=0 returns a usable key and no items. A clean resync is this: deselecting throws the key away, so reselecting starts here.
Push
Skipped entirely for a read-only or download-only folder. Otherwise the queue's pending entries become one or more Sync requests carrying Commands, batched up to the account's item limit. The reply is sparse by design: the server answers only failures, plus the ServerId for each accepted Add. Silence means success.
Instances (16.1)
A recurrence exception is a sibling command carrying the master's ServerId and an InstanceId, so it cannot be sent until the server has assigned that ServerId. Hence its own pass, after the push.
Pull
GetItemEstimate first, so the progress bar means something, then Sync with GetChanges, repeated while the server sets MoreAvailable.

Push before pull is the order [MS-ASCMD] shapes a Sync around, and it is what makes the pull authoritative: our own changes are already part of the state the server reports, so nothing arriving can be an echo that overwrites a pending edit. A genuine two-writer conflict is then decided by the only party that knows both sides — the server — per the <Conflict> preference every request states (1 = server wins, the default; 0 = this device wins). Exchange answers a losing push with Status 7 and delivers the winning copy in the same sync's pull; Z-Push discards the stale change silently with Status 1 and the loser converges on its next pull.

Instance-command requests must not carry <Conflict>. Exchange conflict-checks the exception change against our own just-pushed master and discards it with Status 7 when the element is present; without it the same request gets Status 1.

Recurrence exceptions on 16.x

All in src/modules/eas/calendar-codec.mjs, and all gated on the account's syncRecurrence option (off by default).

Inbound, exceptions arrive in two shapes: embedded, an <Exceptions> block on the master, and per-instance, one <Change> or <Delete> per occurrence carrying airsyncbase:InstanceId.

Outbound on 16.1 it is per-instance only. The embedded block is not accepted in a Sync request — tested against Exchange, which answers Status 6 for the wrapper itself, whether the exception is keyed by InstanceId or ExceptionStartTime, and whether or not it carries <Deleted>. A control run with the block suppressed and nothing else changed was accepted. Both [MS-ASCAL] 2.2.2.21 and [MS-ASAIRS] say otherwise; the server disagrees with both.

Two further rules the wire forced:

  • A cancelled occurrence is a <Delete>, not a <Change> carrying <Deleted> — that is only legal inside the embedded block. The 16.x form is ServerId plus InstanceId, no ApplicationData at all.
  • One instance command per request. Exchange will not take two commands against the same ServerId in one <Commands> block: it applies the first, faults on the second, and answers a global Status 16 that discards the response while keeping what the first did. Every exception of a master shares that master's ServerId.

Only changed exceptions are sent. The queued entry carries a fingerprint of the exception set from before the edit — the cancelled instances, plus each override keyed by RECURRENCE-ID with a digest of its content — so a cancellation the server already has, and an override whose digest has not moved, are skipped. An added item has no baseline and sends everything.

Already-synced items need a one-time re-download (deselect → sync → reselect → sync) before a codec change affects them, so a fix can look inert on existing data.

The server's UID on 16.x

On 16.0/16.1 the client MUST NOT send <UID> ([MS-ASCAL] §2.2.2.46), so the server mints its own and returns it. We never keep it: uploading, applyResponses reads only ClientId, ServerId and Status; downloading, applyAdd generates a fresh crypto.randomUUID() and the server's <UID> is never read.

So on 16.x the iCal UID and the server's UID differ in both directions, invisibly, because nothing consults either — identity uses the EAS ServerId. Verified against a live Exchange Online mailbox: five events uploaded with zero <UID> elements came back after a clean resync carrying server-minted ids. On ≤14.x none of this applies; the UID is client-generated and we send it.

It would start to matter for iTIP traffic, where the UID correlates an invitation with its reply.
