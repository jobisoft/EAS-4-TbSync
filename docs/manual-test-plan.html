Manual test plan

What a person still has to check before a release. Everything scriptable lives in test/ and runs with npm test; what is left here needs a human at the UI — installing, breaking authentication, watching a popup take focus. Sections are lettered M1–M9 so a bare "§6" always means the automated suite.

Before you start

  • Install all three add-ons together. The host refuses any provider whose PROTOCOL_VERSION is not exactly its own.
  • Ask which Thunderbird this is rather than guessing — several installs usually coexist. {"cmd":"getBrowserInfo"}.
  • Read the Event Log first. It lives in storage.session, so a restart wipes it, and debug entries need the log level raised to 3.

A passing item count is not a passing test. items.query and contacts.query read local state, so a check can go green while nothing reached the server. That is not hypothetical: a run throttled with HTTP 503 reported PASS on every step of two sections with an empty wire log, because create-then-delete returns the local count to its baseline whether or not a byte was sent.

So assert the <Add> / <Change> / <Delete> in the Event Log, not only the count. Where what the server holds is the question, finish with a clean pull: deselect the folder, reselect, sync.

After a clean pull, match items by SUMMARY, never by UID. Every item comes back with a freshly minted UID, so a script looking for the one it sent reports the item missing when it is sitting right there. Two causes: [MS-ASTASK] has no UID element at all, and for events the UID is deliberately suppressed on 16.1. Only ≤14.x events keep theirs. This is also why identity across a resync is the ServerId and never the UID.

End every bridge session by deselecting the authorized calendar, then reloading — in that order. Deselecting resets the folder's sync key so the next run starts fresh; reloading mid-sync drops the native port, and since SYNC_FOLDER has no timeout nothing rejects the pending RPC. Only a manual reload in about:debugging recovers it.

M7. Corrupted sync key — resync must not duplicate

This is the identity fallback, and it needs a sync key the server will reject. Set one from the TbSync console:

const K = "tbsync.folders", ID = "1", FID = "<folderId>";
const f = (await browser.storage.local.get(K))[K];
f[ID][FID].custom.synckey = "999999999";
await browser.storage.local.set({ [K]: f });
#StepExpect
M7.1sync a populated folder (20+ items), note the count
M7.2corrupt the sync key, syncserver answers Status 3; the runner resets and re-pulls
M7.3item count unchanged — no duplicatesthe whole point
M7.4custom.indexMap rebuiltthe fallback repopulates it
M7.5the following sync is a normal incremental one
M7.6repeat on a contacts folderdifferent codec

Still unrun. The automated suite covers the clean resync path — no duplicates, index rebuilt, next sync incremental — but that is not a Status 3 resync, so the fallback itself remains unproven.

M9. Cannot be forced — watch for it instead

Rotated refresh tokens. The server decides when to hand back a new one, so this cannot be provoked - only caught. Raise the log level to 3 and use the account normally; when a rotation happens the sync that saw it logs

[oauth] the server rotated the refresh token; stored the new one

which is the whole check: the new token reached storage, so the next start will not come back on a retired one. The token itself is never logged.

If an account ever does ask to authenticate again after a restart, look for that line just before it - its presence or absence says whether a rotation was involved, which is the first thing worth knowing.
