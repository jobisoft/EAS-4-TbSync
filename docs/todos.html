Todos

What is outstanding in EAS-4-TbSync. Host-side work is in the TbSync notes.

Defects

The pull overwrites a pending local edit, then pushes the result back

Repo: EAS-4-TbSync. Reproduced twice.

The push reads the item after the pull pass, so the server's echo of our own earlier push overwrites an edit made before the sync, and the push then sends that echo back. The user's edit is lost silently.

The delete half of this is fixed — applyAdd ignores server data for an item whose deleted_by_user entry is still queued. The edit half needs the same treatment: do not apply a server change to an item carrying a pending modified_by_user entry. Probably pre-existing — the code path is unchanged by the provider-calendar work, only the calendar id differs — but that is unproven.

All-day exceptions cannot bind

Repo: EAS-4-TbSync, calendar-codec.mjs. Unverified — derived by reading the code, no reporter, no server trace.

RECURRENCE-ID and EXDATE are always written as DATE-TIME (jsDateToIcalUtcTime hardcodes isDate: false), while an all-day master's DTSTART is written as a DATE. RFC 5545 §3.8.4.4 requires RECURRENCE-ID to carry the same value type as the master's DTSTART, so for an all-day recurring series an override can never match the occurrence it replaces and an EXDATE can never suppress it.

Same user-visible symptom as #317 — an occurrence that will not move or disappear — for a whole class of events. Affects both inbound paths, since the 16.1 wrapper instanceUtcToIcalTime calls the same writer. v4 sets isDate = true when AllDayEvent == "1".

The fix is presumably to thread the master's all-day flag (already read in applicationDataToIcal) into both writers and build a date-only ICAL.Time. Care needed on the comparison side: removeExdate matches via icalTimeToBasicUtc, which must agree on the representation.

Reconcile with PR #324 first — an open v5 PR against the same file (+104/−28) reworking all-day handling. A different defect, but it moves the ground under this one.

The "Canceled:" title prefix is never stripped

Repo: EAS-4-TbSync. Cosmetic.

Exchange prepends a localized Canceled: to the Subject of a cancelled meeting. v5 computes STATUS=CANCELLED but never strips the word, so the item shows both the strike-through and the redundant prefix — and because it is baked into the stored title it lingers after the occurrence is reactivated.

Niel's v4 fix (NielBuys/EAS-4-TbSync@36c2b916) is a three-line regex strip. Not ported, for two reasons to decide on first: it is lossy (a subject genuinely starting with "Cancelled:" would be rewritten) and English-only (Exchange localizes to the organizer's mailbox language, not the UI language).

Provider-calendar follow-ups

From the review of the provider-calendar switch. Lettering is kept stable as items are fixed and dropped, so gaps are expected.

A. A failed record is accepted anyway. record() in calendar-provider.mjs catches an RPC failure, logs a warning, and still tells the platform the edit succeeded. Port down → the edit is accepted in the UI and never queued. The pre-provider design could not fail this way, since the host recorded it itself. The one correctness risk in this group. Decide between rejecting the edit, retrying, or re-deriving at sync time.

C. The calendar's refresh button does nothing. onSync / onResetSync call handlers that background never sets, so Refresh and "reset sync" in the calendar's properties are silent no-ops.

E. The New Calendar dialog offers our type. The experiment's displayName reads manifest.calendar_provider.name, which the manifest schema does not declare, so the type appears oddly named — and a user can hand-create an unmanaged EAS calendar there.

F. Digest stability on the UI path. A no-op save through items.update demonstrably emits no instance command, so the fingerprint is stable there. A Thunderbird UI edit could still rewrite DTSTAMP/LAST-MODIFIED on overrides; if it does, every override reads as changed and the fingerprint stops earning its keep. Untested.

G. Disabling EAS force-disables its calendars. Data survives, but during any update or disable the user sees disabled calendars. A behaviour change from storage calendars — worth a conscious decision rather than a discovery.

I. Coverage. Verified by driving one live account through the bridge. No automated tests, and multi-account, multi-folder and task folders are untouched.

Unproven

The identity fallback has never run against a live Status 3

Repo: EAS-4-TbSync. See manual test plan §12.

The clean resync path is verified — deselect/reselect leaves no duplicates, rebuilds custom.indexMap, and the following sync is incremental. That is not the same thing: a clean resync is not a server-initiated Status 3, and it is the Status 3 path that exercises the fallback. Needs a deliberately corrupted sync key, which the bridge cannot write.

Existing duplicates are not cleaned up

Repo: EAS-4-TbSync. Accounts that resynced before the blob-stamp rule was in place still carry a duplicate of every item in the affected folder. Nothing removes them. A cleanup needs a matching heuristic and a destructive pass over the user's calendar and address book, deliberately left out rather than guessed at.

Outbound occurrence edits — #334

Repo: EAS-4-TbSync. Was "local occurrence edits never reach the server". The 16.1 per-instance push now exists and has been verified on the wire: moving one override sends exactly one <Change> keyed by InstanceId, and it is accepted. Check whether that closes the issue before assuming it does.

Features and gaps

Keep the server's UID on 16.x

Repo: EAS-4-TbSync. Only wanted if MeetingResponse (#339) needs it — the UID correlates an iTIP reply with the meeting it answers. Establish what that work needs before choosing where to keep one.

The shape would mirror X-EAS-SERVERID: read <UID> inbound in applicationDataToIcal, read it from the <Add> acknowledgement in applyResponses, and let stampEasServerId carry it. One thing to decide: on ≤14.x the iCal UID is the server's UID, so X-EAS-UID would either duplicate it or be absent — pick deliberately, so a reader can tell "not applicable" from "not fetched yet".

Not investigated: ClientUid ([MS-ASCAL] §2.2.2.13) is the mechanism the spec offers a 16.x client for supplying its own identifier. We never send it and it is not in our codepage tables. Whether it makes the server preserve or echo a client-chosen value is unknown.

Log refresh-token rotation

Repo: EAS-4-TbSync. A debug-level Event Log line when a rotated refresh token is stored would turn manual test plan §15 from watch-and-wait into something visible.

MeetingResponse

Repo: EAS-4-TbSync. Contributed feature, deferred. State as of 30 Jul 2026.

The concept

EAS carries an attendee's answer to an invitation in its own command, MeetingResponse, with UserResponse 1 = Accept, 2 = Tentative, 3 = Decline, optionally scoped to one occurrence of a series by InstanceId. The server replies Status 1 and applies the answer to the organizer's tracking and the attendee's copy.

Today an answer travels a different route. Thunderbird's itip engine sets the local PARTSTAT, and the sync pushes that as an ordinary <Add> or <Change>. Exchange reads it as a client creating a self-organized meeting: it makes a second event owned by the person who answered and invites every attendee again (#320; #8, #10, #66 describe the same thing).

In v4, attendee status is inbound only — read from ResponseType and AttendeeStatus, never sent.

Waiting for the server to apply the answer

Status 1 acknowledges receipt; Exchange updates the calendar item afterwards. The panels show that gap and the proposed handling.

Tomas measured the post-response fan-out at ~30 s under load. The 34 s is what the re-poll schedule budgets for itself — 2+4+8+10+10 from settleWaitMs(n) = min(POST_PUSH_WAIT_MS · 2n-1, 10000) over five pulls — with each iteration adding a full pullPhase on top. The measurement is bracketed by the polls that produced it: absent at 24 s, present at 34 s.

A Ping-based listener

EAS has a change-notification channel. The client issues Ping (codepage 13) with a HeartbeatInterval and the Folder ids to watch; the server holds the request open until one of those collections changes or the heartbeat expires, then answers. Supported in every protocol version from 2.5 to 16.1, and the vocabulary is already in wbxml-codepages.mjs.

It behaves as a listener but is built as a loop: the client reissues the request after every response. HeartbeatInterval is cached server-side after the first request, so later ones need only the folder list. Per MS-ASCMD Status (Ping):

  • 2 — something changed; the response names the folders. Sync each, then reissue.
  • 1 — heartbeat expired, nothing changed. Reissue.
  • 5 — heartbeat outside the allowed range; the response carries the nearest allowed value to use.
  • 6 — too many folders; the response carries MaxFolders.
  • 7 — folder hierarchy is stale; FolderSync, then reissue.
  • 3, 4, 8 — missing parameters, malformed WBXML, transient server error.

Applied here, the server's post-response update announces itself: no delay constant, no repeated polling, no sync held open. The same channel covers every incoming change rather than this one case.

A listener fits this better than waiting on a fixed schedule, whatever the constants are set to. A schedule has to guess how long a server will take, and holds the sync open for the length of the guess - which is what locks the account, since a running sync greys out Sync, Remove and Disconnect with no way to cancel (todos.md). Changing the numbers moves the cost between a missed update and a longer lock rather than removing either. The server already knows when it is done, and Ping is how it says so.

What it needs: one held request per account, kept alive across sleep/wake and connection drops; a timeout policy of its own, since the default request timeout is 90 s and a useful heartbeat is longer; and the folder list kept in step with what the user has selected.

Open items

  • Stale-marker guard. The first commit maps ATTENDEESTATUS_TO_PARTSTAT[5] to NEEDS-ACTION. On calendars written by an earlier build, compareSelfPartstat reads a stored ACCEPTED against X-EAS-RESPONSETYPE=5, treats it as a transition, and sends an Accept for an invitation the user never answered — on any local write, including a dismissed reminder. Niel flagged it; Tomas confirmed it and that his test items were all freshly synced. Merge condition.
  • The waiting mechanism needs replacing, not tuning. The re-poll commit on Tomas Kovacik's branch polls on a fixed schedule with the sync held open. Ping is the direction we would rather take. The diagnosis behind it stands - the server really does apply the answer later, and that is worth acting on - but through a listener. If any of that branch is taken as-is in the meantime, its step 4 condition also has to be reconciled with the postPushSettle gate: if ((pushed.changedAnything && ctx.postPushSettle) || ctx.pendingResponseServerIds.size).

Background and what master already covered: How things work.

With an issue

Status 138 protocol fallback → #315. Master handles neither 138 nor 165. The issue title says 165, but the body opens with a Settings response carrying <Status>138</Status> — that is the right target. All one patch, since the pieces depend on each other:

  • PROTOCOL_VERSION_REJECTED_STATUS = "138", AS_VERSION_FALLBACK_ORDER, #switchRejectedAsVersion, versionFallbacksRemaining threaded through #connectAndDiscoverFolders, and a rejectedAsVersions account field cleared on a successful FolderSync.
  • SETTINGS_ERR.REJECTED — today a rejected Settings throws ERR.UNKNOWN_COMMAND, indistinguishable to the caller.
  • easCommand / easAsVersion on the errors thrown by settings.mjs and folder-sync.mjs, so the fallback knows which version was refused.
  • deviceInformationUnsupported — on a rejected Settings, mark the account and continue rather than failing the connect. The direct answer to #315.

Push-rejection diagnostics → #319. reportRejectedPushItem, summarizeBlobForLog, truncateForLog in sync-runner.mjs. #319 is "does not print enough info about The EAS server did not accept 1 elements" — an exact match.

Needs an issue first

  • DURATION with no DTEND. His eventTimingFor derives the end from DURATION, falls back to 1 day / 1 hour, and re-derives when DTEND is not after DTSTART. Master's codec has no duration handling at all.
  • Enabling recurrence sync for Microsoft accounts. Default syncrecurrence false → true for new accounts, runMicrosoftRecurrenceRepair turning it on for existing ones with a forced refetch, and a reworded hint. Changing a setting the user may have chosen is a design decision, not a bug fix.
  • Resetting pinned ActiveSync versions. normalizeMicrosoftProtocolSelection resets asversionselected to auto for known Microsoft hosts carrying a 2.5 / 14.0 / 14.1 pin. Such a pin is a v4 leftover that stops the account ever reaching 16.1.
  • Preferring 16.1 in connect.mjs. The current order is deliberate — 14.1 leads because the codecs are most reliably tested against it. Preferring 16.1 makes hitting 138 more likely, so the fallback has to land first.
  • Restoring rejected pushes. tryRestoreRejectedCalendarItem and friends put the local item back to its last-known blob when the server refuses a push. Right instinct; needs a discussion of when it should and should not fire.
