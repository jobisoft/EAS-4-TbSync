Test plan

Split by who can run it: the bridge drives Thunderbird from a shell, so those checks are scriptable; the rest need a human at the UI. Everything has been run against a live Exchange mailbox unless it says otherwise.

Before you start

Install all three together. The host refuses any provider whose PROTOCOL_VERSION is not exactly its own.

Which Thunderbird is this? Ask, do not guess — several installs usually coexist:

{"cmd": "getBrowserInfo"}   →  {"name":"Thunderbird","version":"153.0.1", …}

The Event Log lives in storage.session, so a restart wipes it. Read it first. debug entries need setLogLevel raised to 3.

A passing item count is not a passing test. items.query and contacts.query read local state, so every check here can go green while nothing reached the server at all. That is not hypothetical: a run that earned an HTTP 503 — forty syncs in a few minutes will — reported PASS on every step of sections 2 and 5 with an empty wire log, because create-then-delete returns the local count to its baseline whether or not a single byte was sent.

So assert the <Add> / <Change> / <Delete> in the Event Log, not only the count. And where what the server holds is the actual question, finish with a clean pull: deselect the folder, reselect it, sync. That drops the local copy and re-fetches everything, which is the only way to see what was stored rather than what was sent.

End every bridge session by deselecting the authorized calendar, then reloading — in that order. Deselecting resets the folder's sync key so the next run starts fresh, and reloading mid-sync drops the native port: SYNC_FOLDER has no timeout, so nothing rejects the pending RPC and only a manual reload in about:debugging recovers it.

Digest selectivity — needs more than one override

3.4 cannot prove the fingerprint works: its fixture has a single override, so "exactly one <Change>" is satisfied whether the digest skips the unchanged ones or there were none to skip. Selectivity only shows up with several. No fixture — build it inline: a weekly series of four from 20260907T090000Z with overrides on the 14th, 21st and 28th, distinct SUMMARY each.

#StepExpect
3.8create, syncmaster <Add>, then one instance command per override
3.9read the item, note each override's DTSTAMP / LAST-MODIFIED
3.10items.update changing one override's SUMMARY, then re-readthe other two overrides' stamps are untouched — the digest covers the whole serialised VEVENT, so a restamp would make every override read as changed
3.11syncone master <Change>, and exactly one instance <Change> — carrying the InstanceId of the edited occurrence only

3.10 answers whether Thunderbird rewrites DTSTAMP / LAST-MODIFIED on components it did not touch. Measured 4 Aug 2026: it does not — the stamps held and no LAST-MODIFIED was added at all, so the fingerprint stays meaningful across the items.update path. What is still unmeasured is an edit made in Thunderbird's own event dialog, which builds the item itself rather than taking ours verbatim; that needs a human.

3.11 currently fails at the server. The selection is right — one instance command, for the edited occurrence, the other two correctly skipped — but Exchange answers Status 6 and the folder ends the sync at warning:

[event-sync] server rejected instance change 20260921T090000Z … (Status 6)

The payload looks well-formed — ServerId + airsyncbase:InstanceId + ApplicationData, one command in its own request. What differs from 3.4 is that the master <Change> goes in the same sync, immediately before it, since editing an override rewrites the whole local item. Whether that is what the server objects to is unestablished. Not a regression from the recurrence work: the instance payload carries no <Recurrence>, and the master's is byte-identical to before that change.

5. Task recurrence

Needs the tasks grant; pass resource: "tasks" on the items.* verbs. Every rule goes in its own sync, so a rejection names the rule that caused it rather than the batch.

[MS-ASTASK] 2.2.2.31 qualifies each recurrence type with further elements — DayOfWeek for weekly, DayOfMonth for monthly, DayOfMonth + MonthOfYear for yearly, plus WeekOfMonth for the nth-weekday forms. Emit the type without them and the server rejects the whole <Add> with Status 6. Daily needs none, which is why it was the only recurring task that could be created until Aug 2026 — and why a green daily case proves almost nothing on its own.

All rules use DTSTART:20260901T080000Z, deliberately: 1 Sep 2026 is a Tuesday and the 1st of month 9, so each implied field has a value you can check by eye.

#RRULEExpect on the wire
5.1FREQ=DAILY;COUNT=4Type 0, no qualifying element
5.2FREQ=WEEKLY;COUNT=4Type 1 + DayOfWeek 4 — filled from DTSTART, which iCal leaves implicit and EAS will not
5.3FREQ=WEEKLY;BYDAY=MO,WE;COUNT=4Type 1 + DayOfWeek 10 (2\|8)
5.4FREQ=WEEKLY;INTERVAL=2;COUNT=4Interval 2 survives
5.5FREQ=MONTHLY;COUNT=4Type 2 + DayOfMonth 1
5.6FREQ=MONTHLY;BYDAY=2TU;COUNT=4Type 3 + DayOfWeek + WeekOfMonth 2
5.7FREQ=YEARLY;COUNT=4Type 5 + DayOfMonth 1 + MonthOfYear 9
5.8FREQ=YEARLY;BYDAY=1MO;BYMONTH=9;COUNT=4Type 6 + WeekOfMonth as well
5.9FREQ=DAILY;UNTIL=20261001T000000ZUntil instead of Occurrences
5.10push all nine, then a clean pulleach rule comes back semantically unchanged

Pass for 5.1–5.9 is the folder staying success with no rejection warning and the changelog emptying. A rejected rule does not merely fail: it is re-staged and retried on every subsequent sync, so the folder sits at warning until the task is deleted. Delete the probe before moving on, or the next case inherits the failure.

5.10 is the step that matters, and the one that found a real bug. The rules come back with their implied fields made explicit — FREQ=WEEKLY returns as FREQ=WEEKLY;BYDAY=TU, FREQ=YEARLY as FREQ=YEARLY;BYMONTHDAY=1;BYMONTH=9 — which is correct and is exactly what the qualifying elements are for. What is not correct is anything else changing: 5.9 used to return UNTIL=20261001T000000, having lost its Z and become a floating time, which RFC 5545 forbids beside a UTC DTSTART.

Match by SUMMARY, not UID. A clean pull mints a fresh UID for every task, because [MS-ASTASK] has no UID element for the server to have stored. Identity is not stable across a resync for tasks, unlike events.

7. Authentication failure

An auth failure stamps the error and nothing else. Break the credentials (change the password in Settings, or corrupt custom.refreshToken from the TbSync console), then restart — the provider caches a good token in memory — and sync.

7.2folder list still listed

12. Corrupted sync key — resync must not duplicate

The identity fallback. The bridge has no storage verb, so this needs the console:

const K = "tbsync.folders", ID = "1", FID = "<folderId>";
const f = (await browser.storage.local.get(K))[K];
f[ID][FID].custom.synckey = "999999999";
await browser.storage.local.set({ [K]: f });
#StepExpect
12.1sync a populated folder (20+ items), note the count
12.2corrupt the sync key, syncserver answers Status 3; the runner resets and re-pulls
12.3item count unchanged — no duplicatesthe whole point
12.4custom.indexMap rebuiltthe fallback repopulates it
12.5the following sync is a normal incremental one
12.6repeat on a contacts folderdifferent codec

Still unrun. The bridge covers the clean resync path — no duplicates, indexMap rebuilt, next sync incremental — but that is not a Status 3 resync, so the fallback itself remains unproven.

15. Cannot be forced — watch for it instead

Rotated refresh tokens. Microsoft decides when to hand back a new one. Note the stored refreshToken, use the account across several restarts, and re-check. What you are watching for is the absence of a spurious Authenticate prompt after a restart. A debug-level Event Log line on rotation would make this visible; not written yet.
